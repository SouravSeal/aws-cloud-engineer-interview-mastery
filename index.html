01 — Interview Principles

The highest-value part of this guide is learning how to approach unfamiliar questions. Interviewers are evaluating your reasoning, not just whether you can recall service definitions.

1. ClarifyDefine the requirement, constraints, scale and success criteria.
2. DecomposeBreak the problem into application, network, identity, data and platform layers.
3. HypothesizeGenerate the most likely causes or design options before jumping to a fix.
4. ValidateUse metrics, logs, configuration and controlled tests to prove or eliminate hypotheses.
5. RecommendExplain the solution, trade-offs, risks and operational consequences.
Golden rule: Do not answer a scenario question with a service name first. Start with the problem, assumptions and decision criteria. Then introduce the AWS service that best satisfies them.

What strong candidates demonstrate

  • Clear technical reasoning rather than memorised terminology.
  • Security and least-privilege thinking by default.
  • Awareness of availability, scalability, observability and failure modes.
  • Ability to distinguish a quick mitigation from a durable engineering fix.
  • Ability to communicate trade-offs instead of presenting one design as universally correct.

03 — Question Bank Preview

Each final question will include the interviewer intent, a structured reasoning path, model answer, common mistakes and follow-up questions.

FOUNDATIONNetworking

What is the difference between a public subnet and a private subnet?

Interview principle: Explain the routing behavior, not simply the label. A subnet is considered public when its route table provides a path to an Internet Gateway; a private subnet does not have that direct route. Then discuss how outbound internet access can be provided through a NAT pattern when required.
SCENARIOTroubleshooting

An EC2 instance is running, but users cannot reach the application. How do you troubleshoot it?

Strong approach: Start from the client and move toward the workload: DNS → load balancer/listener → target health → security groups → NACLs → route tables → subnet connectivity → instance OS/firewall → application process → application logs. State what evidence you would inspect at each layer before changing anything.
ADVANCEDIAM

An EC2 instance has an IAM role attached, but an application receives AccessDenied. What would you check?

Strong approach: Verify the identity actually being used, the role credentials available to the workload, identity-based policies, resource-based policies where applicable, explicit denies, permission boundaries, session policies and organization-level controls such as SCPs. Avoid assuming that “the role has the permission” means the effective permission exists.
SCENARIOGenerative AI on AWS

Design a production RAG application on AWS for enterprise documents containing sensitive information. How would you approach it?

Strong approach: Clarify users, data sensitivity, latency, scale and response-quality requirements first. Then reason through secure ingestion, document processing, embeddings, vector retrieval, foundation-model selection, access control, encryption, network isolation, prompt/context handling, guardrails, observability, evaluation, failure handling and cost. Explain why each component is chosen and identify the main trade-offs.
SCENARIODatabases

Your production database has increasing read traffic. What options would you evaluate?

Strong approach: First identify whether the bottleneck is reads, writes, connections, storage or compute. Then evaluate read replicas/read scaling, caching, query optimization, connection pooling and application changes. Explain why scaling the database blindly may solve the symptom without solving the workload pattern.
