01 — Interview Principles

Strong candidates don't just know AWS services. They demonstrate structured reasoning, operational awareness and the ability to make defensible engineering decisions.

1. ClarifyRequirements, constraints, scale, users and success criteria.
2. DecomposeApplication, network, identity, data, platform and operations.
3. HypothesizeLikely causes or viable designs before choosing a service.
4. ValidateMetrics, logs, configuration and controlled tests.
5. RecommendSolution, trade-offs, risks and operational consequences.
Golden rule: Don't lead with an AWS service. Lead with the problem and decision criteria, then select the service that best satisfies them.

Think in failure domains

Ask what happens when an instance, AZ, dependency, network path, region or external service fails.

Make trade-offs explicit

Strong answers explain why a design is preferred and what it costs in complexity, latency, availability or money.

Separate mitigation from root cause

A production workaround may restore service. A good engineer also explains how the underlying failure will be prevented.

03 — Question Bank

The final bank is designed around the way interviewers probe depth: concept → application → scenario → troubleshooting → architecture → follow-up.

FOUNDATIONNetworking

What is the difference between a public subnet and a private subnet?

Reveal interview-grade approach
What the interviewer is testing: routing fundamentals. Explain the route table behavior rather than treating “public” as a label. A subnet is public when its route table has a route to an Internet Gateway; a private subnet does not have that direct route. Then discuss how outbound access can be provided through a NAT pattern when required.

Follow-up: Why might you prefer a VPC endpoint instead of NAT for access to an AWS service?
TROUBLESHOOTINGEC2 / Networking

An EC2 instance is running, but users cannot reach the application. How do you troubleshoot it?

Reveal interview-grade approach
How to think: move from the client toward the workload: DNS → load balancer/listener → target health → security groups → NACLs → route tables → subnet connectivity → OS firewall → application process → application logs. State what evidence you would inspect at each layer before making changes.

Common mistake: immediately restarting the instance without establishing where the failure occurs.
ADVANCEDIAM

An EC2 instance has an IAM role attached, but an application receives AccessDenied. What would you check?

Reveal interview-grade approach
Strong answer: verify the identity actually being used, credentials available to the workload, identity policies, resource policies where applicable, explicit denies, permission boundaries, session policies and organization-level controls such as SCPs. Explain that an attached role does not automatically mean the requested action is effectively allowed.
SCENARIODatabases

Your production database has increasing read traffic. What options would you evaluate?

Reveal interview-grade approach
Strong answer: first identify whether the bottleneck is reads, writes, connections, storage or compute. Then evaluate query optimization, caching, read scaling/read replicas, connection pooling and application changes. Explain why scaling the database blindly can solve the symptom without solving the workload pattern.
GENAI SCENARIOGenerative AI on AWS

Design a production RAG application on AWS for enterprise documents containing sensitive information. How would you approach it?

Reveal interview-grade approach
What the interviewer is testing: whether you can connect GenAI to cloud engineering fundamentals. Clarify users, data sensitivity, latency, scale and quality requirements. Then reason through secure ingestion, document processing, embeddings, vector retrieval, model selection, IAM, encryption, network isolation, context handling, guardrails, observability, evaluation, failure handling and cost. Explain the trade-offs instead of simply listing services.

Follow-up: How would you prevent a user from retrieving documents they are not authorized to see?
SCENARIOArchitecture

Design a highly available web application across multiple Availability Zones. What would you consider?

Reveal interview-grade approach
Strong answer: define the availability target first, then distribute compute across AZs behind a load balancer, make the application tier stateless where possible, design database failure handling, remove single points of failure, define health checks, observability, deployment strategy and recovery procedures. The strongest answers also discuss what happens when an entire AZ becomes unavailable.
